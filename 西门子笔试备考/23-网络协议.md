# 第一部分：分层模型

## 1.1 TCP/IP 四层 ↔ OSI 七层 ★
| TCP/IP 四层 | OSI 七层 | 典型协议 | 数据单位 | 设备 |
|---|---|---|---|---|
| **应用层** | 应用/表示/会话 | HTTP、DNS、MQTT、Modbus-TCP、SSL/TLS、FTP、SMTP | 报文 | — |
| **传输层** | 传输层 | **TCP、UDP** | 段（segment）/ 数据报 | — |
| **网络层** | 网络层 | **IP、ICMP、ARP**、路由协议 | 包（packet） | 路由器 |
| **网络接口层** | 数据链路层 + 物理层 | 以太网、WiFi、CAN、串口 | 帧（frame） | 交换机、网卡 |

**一句话记忆**：应用层管"内容"，传输层管"端到端可靠性"，网络层管"怎么从 A 到 B（路由）"，链路层管"一段线路上怎么传"。

## 1.2 封装与解封装 ★
**发送方（自上而下加头）**：
```
应用数据
  → + TCP 头（源/目的端口、seq、ack）      = TCP 段
  → + IP 头（源/目的 IP、TTL、协议号）      = IP 包
  → + 以太网头（源/目的 MAC、类型）          = 以太网帧
  → + 前导码 + FCS 校验                      = 物理信号
```
**接收方（自下而上剥头）**：逐层剥离并交给上层对应协议。

# 第二部分：TCP（核心，必考）

## 2.1 TCP 头部关键字段 ★
| 字段 | 大小 | 作用 |
|---|---|---|
| 源端口 / 目的端口 | 各 16 位 | 区分应用进程 |
| **序列号 seq** | 32 位 | 本报文第一个字节的编号 |
| **确认号 ack** | 32 位 | 期望收到的下一个字节编号 |
| 数据偏移 | 4 位 | 头部长度（20~60 字节） |
| **标志位** | 6 位 | SYN（建立）、ACK（确认）、FIN（结束）、RST（重置）、PSH、URG |
| 窗口大小 | 16 位 | 流量控制（接收方还能收多少） |
| 校验和 | 16 位 | 覆盖头 + 数据 + 伪首部 |
| 紧急指针 | 16 位 | URG 时有效 |

## 2.2 三次握手 ★★★（必须能画）
```
Client                                Server
  |                                     |
  |  ──── ① SYN, seq=x ────────────→    |  LISTEN
  |      （我要建立连接，我的起始序号是 x）  |  → SYN_SENT / SYN_RCVD
  |                                     |
  |  ←── ② SYN+ACK, seq=y, ack=x+1 ──   |  （同意，我的序号 y，确认你的 x+1）
  |                                     |
  |  ──── ③ ACK, ack=y+1 ─────────→     |  → ESTABLISHED
  |      （确认收到你的 y）                |
  |  ESTABLISHED                        |
```

**为什么是三次？**
1. 第一次：客户端告诉服务端"我能发"
2. 第二次：服务端告诉客户端"我能收也能发"
3. 第三次：客户端告诉服务端"我能收"
→ **双方都确认了对方的收发能力**（双向确认需要三次）

**为什么两次不行？** ★★
- 服务端发出 SYN+ACK 后，**无法确认客户端能收到**（自己的包可能丢失）
- 历史失效的旧 SYN 若迟到，服务端会白白建立连接并等待数据（浪费资源），这也是 **SYN Flood 攻击**的基础
- 引出考点：**SYN Flood** → 半连接队列（SYN_RCVD）被塞满 → 防护用 **SYN Cookie**（不保存半连接状态，把信息编码进 seq）

## 2.3 四次挥手 ★★★（必须能画）
```
Client                                Server
  |  ──── ① FIN, seq=u ────────────→    |  FIN_WAIT_1 → CLOSE_WAIT
  |  ←── ② ACK, ack=u+1 ──────────      |  （你的 FIN 我收到了）
  |                                     |
  |  ←── ③ FIN, seq=w ────────────      |  LAST_ACK（我也没数据要发了）
  |  ──── ④ ACK, ack=w+1 ─────────→     |  CLOSED
  |  TIME_WAIT (2MSL)                   |
```

**为什么是四次？** ★★
TCP 是**全双工**，两个方向要各自关闭。收到对方的 FIN 只表示"对方没有数据要发了"，但**我方可能还有数据要发**，所以 ACK 和 FIN 不能合并（除非我方也同时关闭，那可能变成三次）。

**TIME_WAIT 为什么要等 2MSL？** ★★★
1. **保证最后的 ACK 能重传**：若第④步 ACK 丢失，服务端会重发 FIN，此时客户端还能应答
2. **让旧连接的报文在网络中消亡**：避免同一四元组的新连接收到旧连接的延迟报文

MSL（Maximum Segment Lifetime）通常 30s~2min，Linux 固定 2MSL = 60s。

**工程排查考点** ★：
- **TIME_WAIT 过多** = 短连接高并发（正常现象，可用 `SO_REUSEADDR`/长连接/调整内核参数缓解）
- **CLOSE_WAIT 过多** = **应用程序没调用 close()**，是**代码 bug**（不是内核问题）

## 2.4 TCP 状态机 ★
**主动打开**：CLOSED → SYN_SENT → ESTABLISHED
**被动打开**：CLOSED → LISTEN → SYN_RCVD → ESTABLISHED
**主动关闭**：ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
**被动关闭**：ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
**同时关闭**：FIN_WAIT_1 → CLOSING → TIME_WAIT

**考试只需记住**：TIME_WAIT 在**主动关闭方**，CLOSE_WAIT 在**被动关闭方**。

## 2.5 TCP 如何保证可靠（五条）★★★
1. **序列号 + 确认应答（ACK）**：每个字节都有编号，接收方累计确认
2. **超时重传**：RTO（Retransmission Timeout）根据 RTT 动态估算
3. **校验和**：覆盖头 + 数据，检测比特错误
4. **流量控制**：滑动窗口，接收方通过 window 字段告知可接收量（防止淹没接收方）
5. **拥塞控制**：慢启动 → 拥塞避免 → 快重传 → 快恢复（防止淹没网络）

## 2.6 拥塞控制四阶段（知道名字与思路即可）
| 阶段 | 做法 |
|---|---|
| **慢启动** | cwnd 从 1 个 MSS 开始，每收到一个 ACK 翻倍（指数增长） |
| **拥塞避免** | cwnd 达到 ssthresh 后改为线性增长（每 RTT +1 MSS） |
| **快重传** | 收到 **3 个重复 ACK** 立即重传（不等超时） |
| **快恢复** | 快重传后 ssthresh 减半，cwnd 从 ssthresh 开始拥塞避免（不回到慢启动） |

## 2.7 TCP vs UDP ★★★（必考对比）
| | **TCP** | **UDP** |
|---|---|---|
| 连接 | **面向连接**（三次握手） | **无连接** |
| 可靠性 | 可靠：有序、不丢、不重复 | 不保证送达/顺序/去重 |
| 传输形态 | **字节流**（无消息边界） | **数据报**（有边界） |
| 头部大小 | 20 字节起 | **8 字节** |
| 流量/拥塞控制 | 有 | 无 |
| 速度 | 慢（开销大） | 快（开销小） |
| 广播/组播 | 不支持 | 支持 |
| 应用 | HTTP/HTTPS、FTP、邮件、数据库、MQTT | DNS、DHCP、音视频、游戏、SNMP |

## 2.8 粘包 / 拆包 ★★★（嵌入式高频）
**原因**：TCP 是**字节流**，没有消息边界。多次 send 的数据可能一次 recv 到（粘包），一次 send 也可能分多次 recv 到（拆包）。
**为什么 UDP 不会**：UDP 保留报文边界，一次 sendto 对应一次 recvfrom。

**三种解决方案** ★：
1. **固定长度**：每个消息固定 N 字节（简单，浪费，只适合定长命令）
2. **特殊分隔符**：如 `\r\n`（AT 命令、Modbus-ASCII 用；但数据含分隔符时不可靠）
3. **长度前缀（TLV）**：包头写 body 长度，**最通用** ← **推荐答这个**
```c
// 协议帧设计
struct Frame {
    uint16_t magic;      // 0xA55A 帧头标记
    uint16_t len;        // body 长度
    uint8_t  cmd;
    uint8_t  payload[];  // 变长
    uint16_t crc;        // 校验
} __attribute__((packed));
```
**接收端处理流程**：环形缓冲区收字节 → 找帧头 → 读 len → 判断是否收齐 → 校验 CRC → 取出一帧。

## 2.9 Nagle 算法与延迟确认（了解）
- **Nagle**：把小包攒起来一起发（省带宽但增加延迟）→ 实时性要求高时用 `TCP_NODELAY` 关闭
- **延迟确认**：收到数据不立即 ACK，等最多 200ms 看能不能捎带
- **两者叠加的坑**：40ms 级别的延迟（经典性能问题）

## 2.10 TCP 保活（Keepalive）
空闲连接定期发探测包，判断对端是否存活。默认 2 小时，可调。嵌入式设备常用应用层心跳代替。

# 第三部分：IP、ARP、ICMP

## 3.1 IPv4 头部关键字段 ★
| 字段 | 作用 |
|---|---|
| 版本 | 4（IPv4） |
| 首部长度 | 20~60 字节 |
| 总长度 | 整个 IP 包长度 |
| 标识 / 标志 / 片偏移 | 分片相关 |
| **TTL** | 生存时间，每经路由器减 1，为 0 丢弃 |
| **协议** | 上层协议：TCP=6、UDP=17、ICMP=1 |
| 源 IP / 目的 IP | 地址 |
| 校验和 | 仅校验头部 |

**TTL 的作用** ★：防止路由环路导致报文无限循环。每经一个路由器减 1，减到 0 丢弃并发 ICMP 超时。`traceroute` 就是利用 TTL 递增实现的。

## 3.2 MTU 与分片 ★
- **MTU**（Maximum Transmission Unit）：链路层能传的最大帧数据，**以太网 1500 字节**
- 超过 MTU 要**分片**（在 IP 层），分片降低效率（任一片丢失整包重传）
- **MSS**（Maximum Segment Size）：TCP 每次能发的最大数据量 = MTU - IP 头(20) - TCP 头(20) = **1460**（以太网）
- TCP 三次握手时会协商 MSS，尽量避免 IP 分片

## 3.3 ARP ★
**作用**：已知 IP 求 MAC 地址（同一局域网内）。
**过程**：广播 ARP 请求"谁是 192.168.1.1？" → 目标主机单播回应自己的 MAC → 缓存到 ARP 表（有超时）。
**跨网段**：ARP 解析的是**默认网关**的 MAC，不是最终目标的 MAC。
**安全**：ARP 欺骗（伪造 ARP 响应）可做中间人攻击。

## 3.4 ICMP ★
- `ping` 用 ICMP Echo Request / Echo Reply
- `traceroute` 用 TTL 递增 + ICMP Time Exceeded

## 3.5 子网划分计算 ★★（常考计算题）
**IP = 网络号 + 主机号**，由**子网掩码**划分。

| 掩码 | CIDR | 总地址数 | 可用主机数 |
|---|---|---|---|
| 255.255.255.0 | **/24** | 256 | **254** |
| 255.255.255.128 | /25 | 128 | 126 |
| 255.255.255.192 | **/26** | 64 | **62** |
| 255.255.255.224 | /27 | 32 | 30 |
| 255.255.255.240 | /28 | 16 | 14 |
| 255.255.255.252 | /30 | 4 | **2**（点对点链路用） |

**公式**：可用主机数 = 2^(32-掩码位数) - 2（减去网络地址和广播地址）

**例题**：192.168.1.0/26
- 子网掩码：255.255.255.192
- 地址范围：192.168.1.0 ~ 192.168.1.63
- 可用主机：192.168.1.1 ~ 192.168.1.62（**62 个**）
- 网络地址（.0）和广播地址（.63）不可用

## 3.6 常见端口（背这些）★
| 端口 | 服务 | 端口 | 服务 |
|---|---|---|---|
| 20/21 | FTP | 123 | NTP |
| 22 | SSH | **161** | SNMP |
| 23 | Telnet | **443** | **HTTPS** |
| 25 | SMTP | **502** | **Modbus-TCP** |
| **53** | **DNS** | **1883** | **MQTT** |
| 67/68 | DHCP | 8883 | MQTT over TLS |
| **80** | **HTTP** | 9600 | OMRON FINS |

## 3.7 NAT（了解）
把私有 IP 转换为公网 IP，解决 IPv4 地址枯竭。
- **SNAT**：内网访问外网（改写源地址）
- **DNAT**：外网访问内网（端口映射/端口转发）

# 第四部分：SSL/TLS（JD 点名）

## 4.1 为什么需要 TLS ★
TCP 只能保证"送到"，不能保证：
- **机密性**：没被偷看 → 加密
- **完整性**：没被篡改 → MAC
- **身份认证**：对端真的是它 → 证书

## 4.2 TLS 握手流程 ★★★（简化到能背）
```
Client                                         Server
  |  ── ① ClientHello ─────────────────────→    |
  |     TLS版本 + 随机数R1 + 支持的加密套件      |
  |                                            |
  |  ←─ ② ServerHello ─────────────────────     |
  |     选定套件 + 随机数R2 + **证书**（含公钥）  |
  |                                            |
  |  ③ 客户端验证证书                            |
  |     CA 链验证、域名匹配、有效期检查           |
  |                                            |
  |  ④ 密钥交换                                 |
  |     RSA: 客户端生成预主密钥，用公钥加密发送    |
  |     ECDHE: 双方用临时DH参数协商（前向保密）   |
  |     → 双方各自用 R1+R2+预主密钥 算出会话密钥  |
  |                                            |
  |  ── ⑤ Finished（验证握手完整性）────────→    |
  |  ←──────── Finished ────────────────────    |
  |                                            |
  |  ⑥ 之后：用**对称密钥**加密通信               |
```

**为什么非对称协商、对称传输？** ★★
非对称（RSA/ECDHE）运算慢约 100~1000 倍，只用来安全地协商出密钥；对称（AES）快，用来传大量数据。

**前向保密（Forward Secrecy）**：用 ECDHE 时，每次会话生成临时密钥对，**服务器私钥泄露也解不开历史流量**。RSA 密钥交换没有这个特性。

## 4.3 证书验证 ★
- 客户端内置 **CA 根证书**（信任锚）
- 服务器证书是 CA 用私钥签名的 → 客户端用 CA 公钥验证签名
- 检查：证书链、有效期、域名（SAN）、吊销状态（CRL/OCSP）

## 4.4 嵌入式用 TLS 的坑 ★★（实战考点）
1. **内存占用大**：证书链验证、AES 运算要 RAM/Flash → 用 **mbedTLS / wolfSSL**（可裁剪）
2. **时间同步**：证书有效期校验需要 RTC 或 NTP。**设备没有正确时间 → 证书验证失败**（这是最常见的实战坑）
3. **证书存储**：放安全存储（SE/TPM/加密 Flash），私钥不能明文存 Flash
4. **硬件加速**：带 AES/SHA 硬件引擎的 MCU 可显著加速（但要注意与 mbedTLS 的适配）
5. **随机数质量**：MCU 的 TRNG 质量差会削弱安全性

# 第五部分：嵌入式联网

## 5.1 Socket 编程 ★★
**TCP 服务器流程**：
```
socket() → bind() → listen() → accept() → recv/send() → close()
```
**TCP 客户端流程**：
```
socket() → connect() → send/recv() → close()
```

| 函数 | 作用 |
|---|---|
| `socket(AF_INET, SOCK_STREAM, 0)` | 创建 TCP 套接字（SOCK_DGRAM = UDP） |
| `bind()` | 绑定 IP + 端口 |
| `listen(fd, backlog)` | 进入监听，backlog = 半连接队列长度 |
| `accept()` | 阻塞等待连接，返回**新的** fd 用于通信 |
| `connect()` | 客户端发起连接（触发三次握手） |
| `send/recv` | 收发数据（TCP）；`sendto/recvfrom`（UDP） |
| `close()` | 关闭（触发四次挥手） |

**考点**：`accept` 返回的是**新套接字**，原监听套接字继续监听。

## 5.2 IO 模型 ★★
| 模型 | 特点 |
|---|---|
| **阻塞 IO** | read 一直等到有数据 |
| **非阻塞 IO** | read 立即返回（EAGAIN），需轮询 |
| **IO 多路复用** | select/poll/epoll，一个线程监控多个 fd |
| **信号驱动 IO** | 数据就绪时发 SIGIO |
| **异步 IO** | 内核完成整个读写后通知 |

**select / poll / epoll 对比** ★（IO 模型视角见 `12-操作系统.md` 5.2）：
| | select | poll | epoll |
|---|---|---|---|
| fd 上限 | 1024 | 无 | 无 |
| 每次调用 | 拷贝全部 fd + O(n) 遍历 | 同 select | 只拷贝一次，事件驱动 |
| 复杂度 | O(n) | O(n) | O(1)（就绪 fd 数） |
| 触发 | 水平触发 | 水平触发 | 水平(LT)/边缘(ET) |

**嵌入式**：资源受限通常用**阻塞 + 多线程**或**简单状态机**，不用 epoll（Linux 网关除外）。

## 5.3 lwIP（轻量协议栈）★
ARM/MCU 上最常用的 TCP/IP 协议栈，可裁剪到几十 KB RAM。
三种 API：
- **raw API**：回调式，无 OS 依赖，最省内存
- **netconn API**：顺序式，需要 OS
- **socket API**：类 BSD，需要 OS，代码可移植

## 5.4 MQTT ★★（IoT 必考）
**轻量级发布/订阅协议**，专为低带宽、高延迟、不可靠网络设计。
- 基于 **TCP**
- 三种角色：**发布者（Publisher）、代理（Broker）、订阅者（Subscriber）**
- **主题（Topic）**：层级用 `/` 分隔，如 `devices/123/temp`
- **通配符**：`+` 单层、`#` 多层
- **QoS 三级**：
  - **QoS 0**：最多一次（可能丢）
  - **QoS 1**：至少一次（可能重复）
  - **QoS 2**：恰好一次（四次握手，最可靠最慢）
- **遗嘱消息（LWT）**：客户端异常断开时，Broker 代为发布预设消息（用于掉线告警）
- **保留消息（Retained）**：Broker 保存最后一条，新订阅者立即收到
- **心跳（Keepalive）**：定期 PINGREQ/PINGRESP
- **报文头最小 2 字节**

**MQTT vs HTTP（IoT 场景）**：
| | MQTT | HTTP |
|---|---|---|
| 模式 | 发布/订阅（异步） | 请求/响应（同步） |
| 开销 | 极小（2 字节头） | 大（文本头） |
| 连接 | 长连接 | 短连接（或 keep-alive） |
| 双向 | 天然支持推送 | 需轮询/WebSocket |
| 适合 | 大量设备上报 | 网页/接口 |

## 5.5 Modbus ★★（西门子工业场景必考）
### Modbus RTU
- 物理层：**RS485**（也用 RS232）
- **二进制编码**，紧凑
- **CRC16** 校验
- **帧分隔靠时间**：3.5 个字符时间的静默
- 地址 1~247（0 = 广播）

### Modbus TCP
- 物理层：以太网，端口 **502**
- **MBAP 头**（7 字节：事务号 2 + 协议号 2 + 长度 2 + 单元号 1）
- **无 CRC**（由 TCP 保证）
- 无需时间分帧

## 5.6 IO-Link（JD 点名）★
- **单对线**三线制：L+（24V）、L-（GND）、**C/Q**（通信线）
- **点对点**（一个主站端口接一个设备），不是总线
- 三种速率：**COM1 4.8 kbps / COM2 38.4 kbps / COM3 230.4 kbps**
- 数据分三类：**过程数据（PD，周期）+ 参数数据（SPDU，非周期）+ 事件**
- **IODD**：设备描述文件（XML），描述参数和结构
- 特点：**既供电又通信**（3 线即可），支持设备参数化、远程配置、诊断
- 定位：传感器/执行器层面的数字化接口（PLC 之下、传感器之上）

# 第六部分：题目（30 题，答案已给）

## 分层与基础

### Q1 ★ 画出 TCP/IP 四层与 OSI 七层的对应关系，列出各层典型协议。
**答案**：见 1.1。
应用层（HTTP/DNS/MQTT/Modbus-TCP/TLS）→ 应用/表示/会话
传输层（TCP/UDP）→ 传输层
网络层（IP/ICMP/ARP）→ 网络层
网络接口层（以太网/WiFi）→ 数据链路 + 物理层

### Q2 ★ 数据从应用层发出到链路上，经历什么封装？
**答案**：应用数据 → 加 TCP 头（端口/seq）变成段 → 加 IP 头（IP/TTL/协议号）变成包 → 加以太网头（MAC）变成帧 → 物理层发送。接收端反向剥离。

### Q3 ★ TTL 的作用是什么？traceroute 如何利用它？
**答案**：TTL（生存时间）每经一个路由器减 1，减到 0 丢弃并发 ICMP 超时——防止路由环路导致报文无限循环。
traceroute 发 TTL=1、2、3… 的包，每跳返回超时消息，从而逐跳发现路径。

### Q4 ★★ 子网划分：192.168.10.0/26 有多少可用主机？范围是多少？
**答案**：/26 = 掩码 255.255.255.192，主机位 6 位 → 2^6 = 64 个地址，减网络地址和广播地址 = **62 个可用**。
范围：192.168.10.0（网络）~ 192.168.10.63（广播），可用 192.168.10.1 ~ 192.168.10.62。
（若 /26 的第 2 个块则是 192.168.10.64~127，依此类推每 64 个一段）

### Q5 ★ ARP 的作用？跨网段时解析谁的 MAC？
**答案**：ARP 把 IP 地址解析成 MAC 地址（广播请求、单播应答、缓存有超时）。
跨网段时 ARP 解析的是**默认网关**的 MAC，因为数据要先发给网关再由它转发。

### Q6 ★ MTU 和 MSS 的关系？
**答案**：MTU 是链路层最大传输单元（以太网 1500 字节）；MSS 是 TCP 单次最大数据量 = MTU - IP头20 - TCP头20 = **1460**（以太网）。TCP 握手时协商 MSS 以避免 IP 分片。

## TCP

### Q7 ★★★ 画出 TCP 三次握手，说明为什么不能是两次。
**答案**：见 2.2。
两次不行：① 服务端无法确认客户端能收到自己的包 ② 历史失效的 SYN 迟到会让服务端白建连接（浪费资源，SYN Flood 基础）。

### Q8 ★★★ 画出 TCP 四次挥手，TIME_WAIT 为什么等 2MSL？
**答案**：见 2.3。
2MSL 两个原因：① 保证最后 ACK 丢失时还能重传 ② 让旧连接的报文在网络中消亡，避免污染新连接。

### Q9 ★★ 大量 CLOSE_WAIT 说明什么问题？大量 TIME_WAIT 呢？
**答案**：
CLOSE_WAIT 大量堆积 = **应用程序没有调用 close()**，是代码 bug（被动关闭方未关闭）。
TIME_WAIT 大量 = 短连接高并发（主动关闭方正常现象），可用长连接或调内核参数缓解。

### Q10 ★★ TCP 如何保证可靠传输（五条）？
**答案**：① 序列号 + 确认应答 ② 超时重传（RTO 动态估算）③ 校验和 ④ 流量控制（滑动窗口）⑤ 拥塞控制（慢启动/拥塞避免/快重传/快恢复）。

### Q11 ★ 拥塞控制的四个阶段？
**答案**：慢启动（cwnd 指数增长）→ 拥塞避免（线性增长）→ 快重传（3 个重复 ACK 立即重传）→ 快恢复（ssthresh 减半后拥塞避免，不回慢启动）。

### Q12 ★★★ TCP 和 UDP 的区别？（至少 6 条）
**答案**：连接（面向连接/无连接）、可靠性（可靠有序/不可靠）、传输形态（字节流/数据报）、头部（20 字节/8 字节）、流控拥塞（有/无）、速度（慢/快）、广播（不支持/支持）。
应用：TCP 用于文件/网页/MQTT；UDP 用于 DNS/音视频/游戏/SNMP。

### Q13 ★★★ 什么是粘包？为什么 UDP 不会？如何解决？
**答案**：TCP 是字节流无消息边界，多次 send 可能合并接收（粘包）或一次 send 分多次收到（拆包）。UDP 保留报文边界，一次 sendto 对应一次 recvfrom。
解决：① 固定长度 ② 特殊分隔符（\r\n）③ **长度前缀（TLV，推荐）**

### Q14 ★ 设计一个 TCP 上的自定义协议，要处理粘包、校验、超时，说说你的方案。
**答案**：帧格式：`magic(2) + len(2) + cmd(1) + payload(len-1) + crc16(2)`。
接收流程：环形缓冲区累积字节 → 搜 magic 定位帧头 → 读 len 判断是否收齐 → 校验 CRC → 分发到 cmd 处理函数 → 从缓冲区移除。
超时：应用层心跳（每 N 秒发一次 ping，M 秒无响应判掉线）+ 指数退避重连。
（这类开放题答出"帧头+长度+CRC+环形缓冲区+心跳重连"就能拿大部分分）

### Q15 ★ 什么是 Nagle 算法？什么场景要关掉？
**答案**：Nagle 把小包攒起来合并发送，减少网络上的小包数量（提高带宽利用率），但增加延迟。
实时性要求高的场景（游戏、远程控制、交互式协议）要关掉（`TCP_NODELAY`）。
坑：Nagle + 延迟确认叠加会导致约 40ms 延迟。

### Q16 ★ TCP 的半连接队列和全连接队列是什么？SYN Flood 如何攻击？
**答案**：半连接队列存 SYN_RCVD 状态（收到 SYN 未完成握手）；全连接队列存已完成握手等待 accept 的连接。
SYN Flood：攻击者大量发 SYN 但不回最后的 ACK → 半连接队列塞满 → 正常连接无法建立。
防护：SYN Cookie（不保存半连接状态，把信息编进 seq）、缩短超时、限流。

## UDP 与应用层

### Q17 ★ 什么场景用 UDP？如何在 UDP 上做可靠传输？
**答案**：场景：实时音视频（容忍丢包但不能卡）、游戏状态同步、DNS、广播/组播、SNMP。
可靠传输：应用层自己做——序列号（检丢包/乱序）、ACK + 重传、超时、去重、可选 FEC 前向纠错（如 QUIC、KCP 的做法）。

### Q18 ★ DNS 解析过程？
**答案**：浏览器/应用 → 本地缓存（hosts、浏览器缓存）→ 本地 DNS 服务器（递归查询）→ 根域名服务器 → 顶级域（.com）→ 权威域名服务器 → 返回 IP。
UDP 53 端口（大数据/区域传送用 TCP）。

### Q19 HTTP 和 HTTPS 的区别？HTTPS 的端口？
**答案**：HTTPS = HTTP + TLS（加密、完整性、身份认证）。端口 HTTP 80，HTTPS **443**。
HTTPS 可以防窃听、防篡改、防冒充，代价是握手开销和 CPU 消耗。

## TLS

### Q20 ★★★ 简述 TLS 握手过程。
**答案**：见 4.2。① ClientHello（版本+随机数 R1+套件列表）② ServerHello（选定套件+随机数 R2+证书）③ 客户端验证证书 ④ 密钥交换（RSA 或 ECDHE 协商出会话密钥）⑤ 双方 Finished 验证 ⑥ 之后用对称密钥加密通信。

### Q21 ★★ 为什么 TLS 用非对称算法协商、用对称算法传输？
**答案**：非对称（RSA/ECDHE）运算慢约 100~1000 倍，只用于安全地协商出会话密钥；对称（AES）快，用于传输大量数据。两者结合兼顾安全与性能。

### Q22 ★ 什么是前向保密？哪种密钥交换支持它？
**答案**：前向保密（Forward Secrecy）：长期私钥泄露也无法解密历史会话。
**ECDHE**（临时椭圆曲线 Diffie-Hellman）每次会话生成临时密钥对，用完丢弃 → 支持前向保密。
RSA 密钥交换不支持（私钥泄露则历史流量全可解）。

### Q23 ★★ 嵌入式设备用 TLS 最容易踩什么坑？
**答案**：① **时间不同步导致证书验证失败**（没有 RTC/NTP，设备时间错误）② 内存/Flash 不够（要用可裁剪的 mbedTLS/wolfSSL）③ 证书和私钥存储不安全（应放 SE/TPM/加密 Flash）④ 随机数质量差 ⑤ 硬件加密引擎适配问题。

## Socket 与嵌入式

### Q24 ★★ 写出 TCP 服务器端和客户端的基本流程。
**答案**：
服务器：`socket() → bind() → listen() → accept() → recv/send → close()`
客户端：`socket() → connect() → send/recv → close()`
要点：`accept` 返回**新的** fd 用于与该客户端通信，监听 fd 继续监听。

### Q25 ★ select / poll / epoll 的区别？
**答案**：select 有 1024 fd 上限、每次调用拷贝全部 fd、O(n) 遍历；poll 无上限但仍是数组 + O(n)；epoll 无上限、只拷贝一次、事件驱动 O(1)、支持边缘触发。高并发用 epoll。

### Q26 ★ lwIP 的三种 API 有什么区别？
**答案**：raw API（回调式，无 OS，最省内存）、netconn API（顺序式，需 OS）、socket API（类 BSD，需 OS，可移植性好）。资源极紧用 raw。

### Q27 ★★ MQTT 是什么？QoS 三个等级的区别？
**答案**：轻量级发布/订阅协议，基于 TCP，适合 IoT。三者角色：发布者、Broker、订阅者。
QoS 0 最多一次（可能丢）；QoS 1 至少一次（可能重复）；QoS 2 恰好一次（四次握手，最可靠最慢）。

### Q28 ★★ MQTT 相比 HTTP 在 IoT 场景的优势？
**答案**：① 报文头最小 2 字节（HTTP 是文本头，几十上百字节）② 长连接 + 发布/订阅，天然支持服务端主动推送 ③ 功耗低（不用频繁建连）④ 支持 QoS 分级可靠性 ⑤ 支持遗嘱消息（掉线告警）、保留消息。
劣势：需要 Broker，协议比 HTTP 复杂，不适合请求/响应式接口。

### Q29 ★★ Modbus RTU 和 Modbus TCP 的区别？常用功能码有哪些？
**答案**：
RTU：RS485 物理层、二进制、**CRC16** 校验、靠 3.5 字符时间分帧、地址 1~247。
TCP：以太网、端口 **502**、**MBAP 头**、无 CRC（TCP 保证）、无需时间分帧。
常用功能码：01 读线圈、03 读保持寄存器、04 读输入寄存器、06 写单寄存器、16 写多寄存器。

### Q30 ★ IO-Link 是什么？有什么特点？
**答案**：工业点对点数字通信接口，用于传感器/执行器层。
三线制：L+（24V）、L-、C/Q（通信）。速率 COM1/2/3 = 4.8k/38.4k/230.4k bps。
数据分过程数据（周期）、参数数据（非周期）、事件。设备用 **IODD** XML 文件描述。
特点：既供电又通信、支持远程参数化与诊断、点对点（非总线）。
